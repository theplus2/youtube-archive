## 절대 규칙

1. **자막 없이 내용을 쓰지 않는다.** 제목·설명·썸네일만 보고 요약이나 전문을 만들지 말 것. 자막 확보에 실패하면 아래 "자막 확보 실패 시" 절차로 가고, 사용자에게 사실대로 알린다.
2. **요약(Mode B)의 모든 주장은 `transcript.txt`에 근거한다.** 영상에 없는 내용, 외부 지식으로 보충한 내용을 화자의 말처럼 쓰지 않는다. 보충 설명이 필요하면 "(편집자 주)"로 구분한다.
3. **파일명·`<h1>`은 `[카테고리명] 영상 제목`**, 폴더명은 `N.[카테고리명]`. 이 규칙은 `build_doc.py`가 강제하므로 `content.json`의 `category`에는 번호·대괄호 없이 이름만 쓴다(예: `신학&교회`).
4. **전문 교정은 요약이 아니다.** 교정본은 원문의 모든 문장을 담아야 한다. 고칠 수 있는 것은 오인식·맞춤법·띄어쓰기·문장부호·
   자막 분절로 깨진 문법뿐이고, 내용을 줄이거나 보태거나 순서를 바꾸지 않는다. 확신이 없으면 고치지 말고 `(?)` 또는 `[불명확]`을 붙인다.
5. `1.[신학&교회]` 분류 영상의 채널·화자가 한국 주요 교단이 이단·사이비로 규정한 단체 소속이면(또는 불확실하면) 문서를 만들기 전에 사용자에게 알리고 진행 여부를 확인한다. 진행 시 `content.json`의 `notes`에 경고 문구를 넣고, `sermon.caution`에도 `[주의]` 또는 `[확인불가]`로 적는다.

## Workflow

### 0단계: 준비

```bash
pip install -q -r requirements.txt
```

**로컬 PC 실행이 기본이다.** 클라우드 세션에서는 YouTube 봇 차단 때문에 1·2순위가 거의 실패하므로, 클라우드에서 실패하면 로컬 실행을 먼저 권한다.
**Windows에서는 아래 모든 `python3`를 `py`로 바꿔 실행한다**(`py -m pip install -r requirements.txt`도 마찬가지).
`python`·`python3`는 Microsoft Store 바로가기일 수 있어 실행되지 않는다(종료 코드 49).
한글 출력이 cp949 오류로 깨지면 명령 앞에 `PYTHONIOENCODING=utf-8`을 붙인다.

Gemini 경로를 쓰려면 `GEMINI_API_KEY`(또는 `GOOGLE_API_KEY`)가 필요하다. 클라우드 환경 설정(세션 제목 표시줄의 환경 메뉴 → Edit)의
Network secrets 또는 환경 변수에 `GEMINI_API_KEY`로 등록되어 있어야 한다. **키를 채팅으로 받지 않는다.**
키가 없으면 3순위 경로만 건너뛰고 나머지는 그대로 동작한다.

### 1단계: 문서 구성 (모드 선택 없음)

모든 문서는 **요약 + 전문** 하나의 형식이다: 설교 활용 태그 → 핵심 명제·시각화 요약(Mode B 부분) → 교정 전문(Mode A 부분).
사용자가 "요약해줘", "전문만", "대본" 등 무엇이라고 하든 둘 다 만든다(둘 다 있어야 문서로서 가치가 있다는 사용자 결정).
`content.json`에 `mode`는 쓰지 않는다. 아래에서 'Mode A'는 전문 부분, 'Mode B'는 요약 부분을 가리킨다.

### 1-1단계: 재생목록 처리 (URL에 `list=`가 있을 때)

URL 종류부터 가른다.

- `youtube.com/playlist?list=...` → 재생목록 전체를 처리한다.
- `watch?v=...&list=...` → 사용자가 "재생목록", "전체", "시리즈"라고 했으면 전체, 아니면 **그 영상 하나만** 처리한다.
  애매하면 AskUserQuestion으로 묻는다.
- `list=RD...`(유튜브 자동 믹스)는 사용자가 만든 목록이 아니므로 전체 처리 전에 꼭 확인한다.

전체를 처리할 때:

1. **목록 받기**

```bash
python3 scripts/yt_fetch.py --list "<재생목록 URL>"
```

   `work/playlist_<LIST_ID>.json`에 `entries`(순번·VIDEO_ID·제목·길이)와 `skipped`(비공개·삭제·중복)가 저장된다.
   목록 단계의 제목은 유튜브가 영어로 자동 번역해 줄 수 있다. 문서 제목은 각 영상의 `meta.json` 제목을 쓴다.
2. **중복 검사를 한 번에.** 각 VIDEO_ID로 Drive `search_files`(`fullText contains '<ID>'`)를 조회해 이미 아카이빙된 영상을 가려낸다.
   재생목록에서는 덮어쓸지 하나씩 묻지 않고 **기본으로 건너뛴다**(사용자가 덮어쓰기를 요청했을 때만 새로 만든다).
3. **진행 전 확인.** 재생목록 제목, 처리할 영상 수, 건너뛸 영상 수(이미 있음/비공개·삭제), 총 재생 시간을 알리고 진행 여부를 묻는다.
   모든 영상이 요약 + 전문(교정 포함)이라 영상당 작업량이 크다. 영상이 많으면(대략 10개 이상) 범위를 고르게 한다(전체 / 처음 N개 / 순번 지정).
   신학&교회 재생목록이면 절대 규칙 5의 채널·화자 확인을 **시작 전에 한 번** 한다.
4. **영상마다 2~4단계를 차례로.** 한 영상의 문서를 Drive에 저장하고 검증한 뒤 다음 영상으로 간다.
   카테고리는 영상마다 따로 고른다(같은 재생목록이라도 다를 수 있다).
   - 자막 확보 실패(종료 코드 3)나 그 밖의 오류는 그 영상만 '실패'로 적고 다음 영상으로 넘어간다. 추측으로 문서를 만들지 않는 규칙은 같다.
   - 처음 2~3개가 연달아 봇 차단으로 실패하면 멈추고 사용자에게 알린다(나머지도 같은 이유로 실패할 가능성이 높다).
   - 여러 영상을 할 때는 영상 하나를 서브에이전트 하나에 맡길 수 있다. 같은 시점에 Drive 폴더를 새로 만드는
     충돌을 피하려고 폴더 ID 확보와 `drive_ids.py` 기록은 메인 세션이 한다.
5. **보고**는 표 하나로: 순번 · 제목 · 결과(완료/이미 있음/실패/비공개) · 카테고리 · 문서 링크. 실패한 영상은 이유를 한 줄로 적는다.

### 2단계: 추출

```bash
python3 scripts/yt_fetch.py "<URL>"
```

`work/<VIDEO_ID>/`에 `meta.json`, `transcript.json`, `transcript.txt`가 생긴다. 종료 코드 3이면 자막 확보 실패다.

자막은 **한 번만, 끝까지** 읽는다(토큰 절약). `transcript.txt`는 읽지 않는다. 곧바로 `clean_transcript.py prep`(3-1단계)을
돌려 청크(`NN.raw.txt`)를 읽고, 그 내용으로 분류·요약·설교 활용 태그·용어 교정표·교정본을 모두 쓴다. 청크는 `transcript.txt`와 같은 내용이다.

전사 확보 순서 (`--via auto`, 기본):

| 순위 | 경로 | 성격 |
| :--- | :--- | :--- |
| 1 | yt-dlp 자막 | 제작자 자막 또는 유튜브 자동 자막 원문 |
| 2 | youtube-transcript-api | 위와 동일, 다른 접근 방식 |
| 3 | `watch` 스킬 → Gemini | YouTube 차단 우회. **AI가 듣고 받아쓴 것**이라 원문 자막이 아님 |

- 이미 차단이 확인된 세션이면 `--via gemini`로 1·2순위를 건너뛰어 시간을 아낀다.
- 원문 자막만 허용하려면 `--via youtube`.
- Gemini 전사(`transcript.kind == "gemini"`)는 누락·오기·환각이 있을 수 있다. 문서에는 경고가 자동으로 들어가며,
  최종 보고에서도 사용자에게 알린다. `coverage`(전사 범위/영상 길이)가 0.9 미만이면 뒷부분 누락 가능성을 따로 알린다.
- Gemini 경로는 영상 URL을 Google에 보낸다. 공개 영상만 대상으로 하고, 비공개·일부공개 영상이면 사용자에게 먼저 묻는다.

**중복 검사**: Drive `search_files`로 `fullText contains '<VIDEO_ID>'`를 조회한다. 이미 문서가 있으면 새로 만들지 말고 사용자에게 링크를 알려 덮어쓸지 묻는다.

#### 자막 확보 실패 시

클라우드 세션의 IP는 YouTube 봇 차단("Sign in to confirm you're not a bot", HTTP 429/403)에 자주 걸린다. 스크립트가 이미 재시도했으므로:

1. 오류가 `GEMINI_API_KEY 미설정`이면 0단계대로 환경 설정에 키를 등록하도록 안내한다(새 세션부터 적용).
2. 1·2순위만 실패하고 Gemini도 일시 오류면 1~2분 뒤 한 번만 더 실행한다.
3. 그래도 실패하면 사용자에게 알리고, 유튜브 영상 설명란의 "스크립트 표시"에서 복사한 텍스트를 붙여넣어 달라고 요청한다 →
   파일로 저장 후 `python3 scripts/yt_fetch.py "<URL>" --transcript-file <파일>` (타임스탬프 줄 자동 인식)
4. 어떤 경우에도 추측으로 문서를 만들지 않는다.
5. `watch` 스킬의 로컬 엔진(yt-dlp 다운로드 + Whisper)은 같은 YouTube 차단에 걸리므로 이 환경에서는 대안이 되지 않는다.

### 3단계: 분류 및 content.json 작성

`config/categories.json`의 `scope`를 기준으로 15개 중 **하나**를 고른다. 두 곳에 걸치면 영상의 주된 논지를 따르고, 판단 근거를 최종 보고에 한 줄로 적는다.
`14.기타통합`은 번호와 상관없이 다른 14개가 모두 맞지 않을 때만 고른다.

영화&드라마 영상의 작성 요령:
- 그림: 줄거리·사건 순서는 `timeline`, 인물 관계·대비는 `cards`·`contrast`, 주제 해석의 구조는 `tree`가 잘 맞는다.
  인물·사건 이름은 영상이 부른 대로 쓰되, 자막 오인식은 용어표로 바로잡는다.
- 설교 활용 태그: 영화는 예화로 쓰기 좋다. 예화 카드의 `facts`에 **작품명·감독·개봉(방영) 연도**를 영상이 말한 대로 넣는다.
  영상이 말하지 않은 정보는 보태지 않는다(절대 규칙 2). 영상의 결말 해석이 화자 개인의 견해면 "(화자 주장)"을 붙인다.

`work/<VIDEO_ID>/content.json`을 작성한다(스키마는 `scripts/build_doc.py` 상단 주석 참조).

- **Mode B `summary`** — 텍스트는 `thesis`뿐이고, 나머지는 모두 다이어그램(`visuals`)으로 요약한다.
  - `thesis`: 핵심 명제. 합쳐서 5~7줄.
  - `visuals`: 다이어그램 4~7개. 각 항목에 `type`, `title`, 선택으로 `start`(초, 제목 옆 딥링크)와 `caption`(그림 아래 한 줄).
    형식은 `scripts/render_visuals.py` 상단 주석에 있다.

    | type | 언제 쓰나 |
    | :--- | :--- |
    | `tree` | 영상 전체 구조 한눈에 보기(주제 → 2~5개 가지 → 요점). **첫 그림으로 거의 항상** |
    | `flow` | 논증의 진행, 단계, 과정, 원인 → 결과 |
    | `cycle` | 서로 맞물려 되풀이되는 관계(선순환·악순환) |
    | `matrix` | 여러 대상을 같은 기준으로 비교(행 = 대상, 열 = 기준). 행에 `icon` 이모지 가능 |
    | `contrast` | 통념 대 실제, 이전 대 이후, 찬성 대 반대 |
    | `layers` | 기초 → 상위로 쌓이는 위계(위가 좁고 아래가 넓다) |
    | `timeline` | 시간·역사 순서, 영상 속 사건 전개 |
    | `cards` | 서로 대등한 핵심 개념·인물·용어 2~6개 |

  - 영상의 논리 구조에 맞는 형태를 고른다. 같은 type을 반복하기보다 내용에 맞게 섞는다.
  - 그림 속 글은 짧게: 상자 하나에 한두 줄(대략 40자 이내). 긴 설명은 `caption`으로. 모든 글은 자막에 근거한다(절대 규칙 2).
  - `style`(선택): `"note"` 손글씨 노트(기본, 생략하면 이것) | `"clean"` 깔끔한 도식. 사용자가 따로 원하지 않으면 생략한다.
    note는 Google Fonts에서 글꼴을 불러오므로 인터넷이 필요하다(못 불러오면 오류로 멈춘다 → 연결 확인 또는 `"clean"`).
  - `python3 scripts/render_visuals.py work/<ID>`로 `work/<ID>/visuals/*.png`를 미리 만든다. 스크립트가 그림마다
    레이아웃을 자동 점검해 `[점검 통과]`/`[점검 경고]`를 출력한다(상자 밖 글자, 순환 노드 겹침, 세 줄 넘는 라벨, 가로 넘침).
    **경고 난 그림만 열어 보고** 글을 줄이거나 type을 바꿔 다시 그린다. 모두 통과면 이미지를 열지 않는다(토큰 절약).
    점검은 화살표 방향·내용의 맞고 틀림은 보지 않으므로 명세를 쓸 때 직접 챙긴다. build_doc.py는 같은 명세·스타일이면 다시 찍지 않는다.
  - Chrome 또는 Edge가 필요하다(없으면 `CHROME_PATH` 환경 변수로 지정). Pillow도 필요하다(`requirements.txt`).
- **Mode A `sections`** (3-1단계 교정을 먼저 끝낸 뒤 쓴다): `{"start": 초, "anchor": "그 문단의 첫 말(선택)", "title": "소제목"}`.
  - 본문 텍스트는 여기 쓰지 않는다. 스크립트가 교정본(3-1단계)에서 채운다.
  - 소제목은 주제가 바뀌는 문단에서 시작한다. 같은 타임스탬프에 문단이 여럿이면 `anchor`로 시작 문단을 지정한다
    (`python3 -c` 로 `clean_transcript.load()` 결과를 출력해 문단 시각·첫 말을 확인).
  - 영상 챕터가 지나치게 길거나 짧으면 쓰지 말고 주제 단위(보통 2~4분)로 직접 나눈다. 생략하면 챕터 → 5분 단위로 자동 분할.
  - `notes`: '읽기 전에' 상자에 넣을 안내(출연자 확인 결과 등). 교정·전사 출처 안내는 스크립트가 자동으로 넣는다.
  - `corrections`: `[["자막 원문", "교정"], ...]` 주요 교정 어휘 20~30개. 문서 끝 부록 표가 된다.
- **`sermon`(필수)**: 3-2단계 참조.
- **`source`(선택)**: 다른 사람의 영상을 다시 올린 채널이면 `{"channel": "원 채널", "title": "원 영상 제목", "url": "원 링크(알면)"}`.
  영상 설명·자막으로 확인되는 것만 쓴다. 머리 정보표에 `원본 출처`로 들어간다(출처 없이는 설교에서 인용하기 어렵다).

### 3-2단계: 설교 활용 태그 (모든 문서 필수)

나중에 설교 준비 때 Drive 전문 검색(예: `"본문: 히브리서"`, `"주제: 고난"`, `"삶: 불안"`)으로 찾기 위한 표다.
`content.json`의 `sermon`에 **구조만** 쓰면 `build_doc.py`가 고정 라벨·표기로 바꿔 머리 정보표 바로 아래(‘읽기 전에’ 위)에 넣는다.
스키마는 `scripts/sermon_tags.py` 상단 주석. 형식이 틀리면 빌드가 멈추고, 기준 어휘 밖의 말·자막에 없는 책 이름은 경고한다.
**태그와 예화 카드도 절대 규칙 2를 따른다**: 영상에 있는 것만 쓴다.

- `level` (설교연결도)
  - `상`: 성경 본문·신학 주제를 직접 다루거나, 설교 예화로 바로 쓸 만한 이야기가 있음
  - `중`: 청년의 삶 문제(돈, 일, 관계, 불안, 정체성, 몸)와 연결할 만한 장면이 있음
  - `하`: 연결점이 거의 없음(기술 튜토리얼, 제품 리뷰 등). `level`만 쓰고 나머지는 비운다 → 표에 "해당 없음", 예화 카드 없음.
    단 `caution`(출처주의)은 '하'여도 해당하면 적는다. 표에 그대로 남는다.
- 목록 칸(`passages`·`words`·`topics`·`life`·`illustrations`·`verify`)은 하나뿐이어도 `[...]`로 쓴다. 문자열이면 빌드가 멈춘다.
  태그 안의 띄어쓰기는 지워진다(`하나님 나라` → `하나님나라`). 구절의 `–`·`~`는 `-`로, 끝의 `장`·`편`은 떼어 낸다.
- `passages` (관련본문): 영상이 **직접 언급하거나 낭독한** 구절만. 연상해서 보태지 않는다.
  `{"book": "히브리서", "ref": "11:1"}` — 책은 개역개정 정식 명칭이나 약어, 약어는 스크립트가 붙인다. 없으면 `[]`.
- `words` (원어): 영상이 언급한 히브리어·헬라어 단어만. `{"word": "כָּבוֹד", "reading": "카보드"}`. 히브리어는 니쿠드(모음 부호)를 넣는다.
  단어 뜻 설명은 요약 쪽에 두고 여기에는 단어만.
- `topics` (신학주제)·`life` (청년삶): 각각 최대 5개. **아래 기준 어휘에서 먼저 고르고**, 맞는 말이 없을 때만 새 말을 쓴다
  (같은 개념이 문서마다 다른 말로 적히면 검색이 안 된다). 목록 원본은 `sermon_tags.py`의 `TOPICS`·`LIFE`.
  - 주제: 믿음, 소망, 사랑, 은혜, 구원, 회개, 성화, 성령, 기도, 예배, 말씀, 교회, 공동체, 고난, 악과고통, 죄, 용서, 십자가, 부활, 종말, 창조, 섭리, 소명, 제자도, 정의, 하나님나라, 이단분별
  - 삶: 불안, 진로, 취업, 일, 돈, 소비, 주거, 관계, 연애, 결혼, 가족, 외로움, 비교, 자존감, 정체성, 실패, 회복, 몸과건강, 습관, 시간, 디지털, AI, 공정, 세대, 죽음
- `illustrations` (예화 카드, 상·중일 때만, 최대 3개): `title` 한 줄 제목, `scene` 영상 속 이야기 2~3문장(사람·장소·사건 중심),
  `facts` 숫자·연도·이름 등 확인 가능한 사실(영상 설명 그대로, 화자의 추정·과장은 그대로 옮기고 "(화자 주장)"), `start` 초,
  `topics`·`life` 연결 가능 주제. **설교 적용이나 신학적 해석은 쓰지 않는다**(해석은 설교 작성 단계에서 한다).
  `예화후보` 칸("예화 N개")은 스크립트가 센다.
- `verify` (확인필요): 학계 논쟁이 있거나 근거 없이 단정한 주장, 확인이 필요한 통계·연대·인용문을 한 줄씩. 없으면 `[]`.
  예: "휘포스타시스=소유권 등기증서 해석: 파피루스 용례 기반, 주석가 간 이견 있음"
- `caution` (출처주의): `"없음"` / `"[주의] 사유 한 줄"`(극단적 번영신학, 신사도운동 계열 등) / `"[확인불가] 화자 소속 미확인"`
  (한국 주요 교단 총회가 규정한 이단·사이비 단체와의 관련을 확신할 수 없을 때). 판단 근거가 없으면 추측하지 말고 `"없음"`.
  절대 규칙 5의 확인 결과와 맞춘다.

### 3-1단계: 전문 교정 (필수)

```bash
python3 scripts/clean_transcript.py prep work/<VIDEO_ID>
```

`work/<ID>/clean/`에 `01.raw.txt …`(약 2,200자 단위 청크)가 생긴다.

1. **용어 교정표 먼저.** 청크(`NN.raw.txt`)를 모두 읽고 오인식된 인명·지명·용어를 `clean/glossary.md`에 정리한다
   (확신하는 교정 / `(?)`를 붙일 추정 / 손대지 않을 불명확 항목을 구분). 출연자 이름은 자기소개·자막·영상 설명으로 확인되는 것만 쓴다.
   - 교정 항목은 `- 자막 원문 → 교정` 형식으로 적는다. 한 줄에 여러 쌍은 ` / `로, 같은 교정의 다른 표기는
     `- 빌리지 / 빌리진 → 빌리 진`처럼 적는다. 괄호 속 메모는 무시된다.
   - `check`는 이 쌍을 원문에 먼저 적용하고 보존율을 잰다. 그래서 고유명사를 고쳐도 '원문 손실'로 세지 않는다.
     **보존율을 맞추려고 맞는 교정을 `[불명확]`으로 되돌리거나 표기를 덧붙이지 말고, 교정 쌍을 용어표에 추가한다.**
     남용 방지: 원문 쪽이 20자(공백 제외)를 넘거나, 교정 쪽이 원문 쪽의 절반보다 짧거나, 교정 쪽 글자가 그 청크 교정본에
     없으면 그 항목은 무시된다. 용어표로 바꾸는 글자는 청크 원문의 12%까지만 인정된다. 빠진 문장은 용어표로 메우지 말고 되살린다.
2. **청크별 교정본 작성.** 각 `NN.raw.txt`를 읽고 `NN.txt`를 쓴다.
   - 문단마다 맨 앞에 `[HH:MM:SS] ` 태그. 그 문단의 첫 말이 들어 있는 원문 줄의 태그를 그대로 복사한다. 시간 역순 금지.
   - 화자가 바뀌면(원문의 `>>`) 새 문단. 한 사람이 길게 말하면 3~6문장마다 자연스러운 곳에서 문단을 나눈다. `>>`는 지운다.
   - 의미 없는 말더듬·중복 단어만 지울 수 있다. `[웃음]` 같은 표기는 둔다. 화자 이름을 지어 붙이지 않는다.
   - 문단은 반드시 문장이 끝나는 곳에서 나눈다(원문 줄 경계에서 나누지 않는다). 말이 끊기면 `…`로 끝낸다.
     문장 부호 없이 끝난 문단은 화자 혼동이 생기므로 `check`가 경고한다.
   - 청크 경계에서 문장이 잘려도 글을 다른 청크로 옮기지 않는다. 마지막 문단을 문장 중간에서 끝내 두면
     스크립트가 다음 청크의 첫 문단을 이어 붙인다.
   - 타임스탬프 없는 사용자 제공 전사는 모든 태그가 `[00:00:00]`이 된다(줄은 약 400자 단위로 나뉜다).
   - 청크가 8개를 넘으면 서브에이전트 여러 개에 나눠 맡길 수 있다. 이때 모두 같은 `glossary.md`와 위 규칙을 따르게 하고,
     돌아온 결과에서 인명 표기가 갈렸는지 `grep`으로 확인해 통일한다.
3. **검사.**

```bash
python3 scripts/clean_transcript.py check work/<VIDEO_ID>
```

다음 중 하나라도 걸리면 실패한다(요약·생략·창작 의심).
- 원문 글자(한글·숫자·영문) 중 교정본에 그대로 남은 비율이 0.88 미만 (용어표의 교정 쌍을 원문에 적용한 뒤 계산)
- 교정본에 대응하는 곳이 없는 원문 연속 구간이 20자 이상 — 출력된 구간을 원문과 대조해 빠진 문장을 되살린다
- 청크 글자 수가 원문의 0.75~1.30배 밖 (0.97 미만은 경고)
`build_doc.py`도 같은 검사를 하므로 통과하지 못하면 문서가 만들어지지 않는다.
교정 없이 원문을 그대로 실어야 할 때만 `content.json`에 `"cleanup": false`를 쓴다(사용자가 원할 때).

### 4단계: 문서 빌드 및 Drive 저장

```bash
python3 scripts/build_doc.py work/<VIDEO_ID>
```

출력 JSON의 `title`, `folder`, `folder_id`, `root_id`, `root_title`, `file_reference`를 사용한다.

Drive 폴더 ID는 **사람마다 다르다**. 실행하는 사람의 Drive 기준 ID를 git에 올리지 않는 `config/drive.local.json`에 두고
`scripts/drive_ids.py`로 읽고 쓴다. `config/categories.json`(공유)에는 ID를 쓰지 않는다. 저장소를 처음 받은 사람은
이 파일이 없으므로 `root_id`·`folder_id`가 `null`로 나오고, 아래 순서대로 자기 Drive에 폴더를 찾거나 만든다.

1. **루트 폴더 ID 확보** (`root_id`가 `null`일 때만)
   - `search_files(query="title = '<root_title>' and mimeType = 'application/vnd.google-apps.folder' and owner = 'me' and trashed = false")`
   - 하나면 그 ID. 여럿이면 AskUserQuestion으로 어느 것인지 묻는다(남이 공유한 폴더가 아니라 본인 폴더인지 확인).
   - 없으면 `create_file(title="<root_title>", contentMimeType="application/vnd.google-apps.folder")`로 내 드라이브 맨 위에 만든다.
   - `python3 scripts/drive_ids.py set-root <ID>`로 기록한다.
2. **카테고리 폴더 ID 확보** (`folder_id`가 `null`일 때만)
   - `search_files(query="parentId = '<root_id>' and title = '<folder>' and trashed = false")`로 찾는다.
     `title contains '영상&음향'`은 `AI 영상&음향 제작`까지 걸리므로 `=`로 정확히 찾는다.
   - 없으면 `create_file(title="<folder>", contentMimeType="application/vnd.google-apps.folder", parentId="<root_id>")`로 만든다.
   - `python3 scripts/drive_ids.py set "<카테고리명>" <ID>`로 기록한다. 개인 설정이라 **커밋하지 않는다**.
   - 처음 쓰는 사람의 첫 보고에는 루트·카테고리 폴더를 새로 만들었는지 알린다. `drive_ids.py show`로 현재 상태를 볼 수 있다.
2. **문서 생성** — Google Drive 커넥터 `create_file`:
   - `title`: 출력의 `title` 그대로
   - `contentMimeType`: `text/html` (Drive가 Google Docs로 자동 변환)
   - `parentId`: 카테고리 폴더 ID — **생성 시점에 지정하므로 별도 이동이 필요 없다**
   - 본문: `base64Content`에 출력의 `file_reference` 문자열을 그대로 넣는다(파일 내용을 직접 타이핑하지 않음). 경로 구분자는 `/`로 바꿔 넣는다.
     해시 불일치로 거부되면 `sha256sum work/<ID>/doc.html`로 다시 계산해 넣는다. 그래도 안 되면 `doc.html`을 읽어 `textContent`로 전달한다.
3. **검증** — 응답의 `mimeType`이 `application/vnd.google-apps.document`이고 `parentId`가 카테고리 폴더인지 확인한다. 아니면 `update_file(fileId, parentId)`로 바로잡는다.

## 서식 표준 (build_doc.py가 적용 — 수정은 스크립트에서)

Google Docs의 HTML 가져오기에서 살아남는 속성만 쓴다(인라인 스타일, 표 셀 배경·테두리, 글꼴·크기·색·굵기, 문단 여백·줄 간격).
문단 배경·좌측 강조선·flex·클래스 CSS는 유실되므로 쓰지 않는다. 디자인 값은 스크립트 상단 '디자인 토큰'에 모여 있다.

- 글꼴 **Noto Sans KR**(Docs 기본 제공. 맑은 고딕은 Docs에 없어 Arial로 바뀐다). 본문 11pt, 왼쪽 정렬, 줄 간격 1.7, 문단 뒤 10pt.
- 색: 본문 `#202124`, 보조 `#5f6368`, 강조(제목·소제목·표 머리) 남색 `#1f4e8c`.
- 머리말: 작은 남색 머리글(아카이브·요약 + 전문) → `<h1>` `[카테고리] 영상 제목` → 정보 표(영상·채널·게시일·길이·전사 출처·원본 출처) →
  `설교 활용 태그` 표(항목 | 내용, 고정 라벨 8개) → 예화 카드(`예화 카드 N: 제목` + 장면·핵심 사실·시각 링크·연결 가능 주제) → 노란 '읽기 전에' 상자.
- 문서 형식은 하나뿐이다: 머리글 "요약 + 전문". 아래 Mode B 부분(요약) 뒤에 Mode A 부분(전문)이 이어진다.
- Mode A: 목차 표(시각 링크 + 번호 + 소제목) → `01  소제목` 형식 소제목 + "▶ 시작–끝 영상에서 보기" 링크 →
  문단마다 앞에 회색 작은 타임스탬프 링크(1시간 미만 영상은 `mm:ss`) → 부록 '주요 교정 어휘' 표 → 바닥글(버전·아카이빙 날짜).
- Mode B: `1. 핵심 명제`(하늘색 상자) → `2. 시각화 요약`(그림마다 제목 + ▶ 딥링크 + PNG + 캡션).
  그림은 900px 폭으로 2배율 렌더링해 문서 본문 폭(468pt)에 맞춘다. 스타일별 색·CSS는 `render_visuals.py`의 NOTE/CLEAN과 note_css/clean_css.
- 상자는 1칸 표로 구현한다. 이모지 등 BMP 밖 문자는 숫자 참조로 바꿔 Drive 변환에서 깨지지 않게 한다.
- 타임스탬프 링크는 `https://www.youtube.com/watch?v=<ID>&t=<초>s`. 썸네일·스틸컷 등 이미지는 넣지 않는다.
